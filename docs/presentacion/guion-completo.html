Arquitectura

El backend publica un evento (topic) y un comando (direct); el procesador consume las tres colas y lo que no puede procesar termina, vía el DLX, en la DLQ de su cola. Este diagrama es lo que muestran la Parte 1 y el bloque 1 de la Parte 3.

Parte 1 – Integrante 2: arquitectura y seguridad (2:00 – 2:30)

En pantalla: el diagrama de la página de Arquitectura, a pantalla completa. Señala con el mouse cada caja cuando la nombres.

1. Presentación · 15 s

Muestra: el diagrama completo.

"Hola, somos el equipo de Pedidos360. Les vamos a mostrar cómo incorporamos mensajería asíncrona con RabbitMQ al sistema que construimos en la evaluación anterior. Yo explico la arquitectura, Sebastián muestra la demo en la nube y [nombre del Integrante 3] explica el código."

2. Punto de partida · 20 s

Señala: Microsoft Entra ID, Frontend Angular y API Gateway (fila de arriba) y Amazon RDS.

"Pedidos360 ya tenía un frontend en Angular con inicio de sesión en Microsoft Entra ID, un backend en Spring Boot con base de datos MySQL en Amazon RDS, y un API Gateway en AWS como API Manager. Ahora, al crear un pedido, hay tareas que no deben hacer esperar al usuario: avisar al cliente, generar un ticket y generar el comprobante."

3. Flujo de un pedido · 45 s

Señala: backend → pedidos.events.exchange → notificaciones.queue y tickets.queue; luego pedidos.tasks.exchange → documentos.queue; al final procesador-service.

"El usuario crea el pedido en Angular. El API Gateway valida el token y lo envía al backend, que guarda el pedido en RDS y publica dos mensajes en RabbitMQ. El primero es el evento pedido.creado, que va a un exchange de tipo topic: la cola de notificaciones está enlazada con el patrón pedido.*, así que recibe cualquier evento de pedido, y la cola de tickets solo con pedido.creado. El segundo es el comando documento.generar, que va a un exchange de tipo direct y llega solo a la cola de documentos, por coincidencia exacta. Un tercer microservicio, el procesador, consume las tres colas."

4. Qué pasa cuando algo falla · 30 s

Señala: procesador-service → pedidos.dlx → las tres DLQ (las cajas en color).

"Si el procesamiento falla por algo transitorio, el procesador reintenta tres veces con espera creciente de 1 y 2 segundos. Si sigue fallando, o si el error es permanente como un dato inválido, rechaza el mensaje y RabbitMQ lo reenvía al Dead Letter Exchange, que lo deja en la DLQ de esa cola. Cada DLQ guarda los mensajes hasta 24 horas y máximo 10.000. Y si RabbitMQ estuviera caído, el pedido igual se guarda: la mensajería no rompe la lógica existente."

5. Administración e infraestructura · 20 s

Señala: rabbit-admin-service, el recuadro "Clúster RabbitMQ (2 nodos)" y el recuadro de la EC2.

"Agregamos un microservicio administrador con una API REST para crear y eliminar colas, exchanges y bindings, y para monitorear las DLQ. RabbitMQ corre como un clúster de dos nodos levantado con docker compose en una instancia EC2."

6. Seguridad · 20 s

Señala: Microsoft Entra ID y API Gateway.

"El token JWT de Entra ID se valida en dos capas: primero en el API Gateway, con un autorizador JWT que revisa el emisor y la audiencia; después en cada microservicio, que revisa firma, emisor, audiencia, vigencia y roles. Crear pedidos exige el rol Cliente y modificar RabbitMQ exige el rol Admin."

7. Cierre y traspaso · 5 s

"Ahora Sebastián les muestra todo funcionando en la nube."

2. Nombres centralizados · 25 s

Muestra: procesador-service/src/main/resources/application.yml

pedidos360:
  messaging:
    exchanges:
      events: pedidos.events.exchange        # TOPIC
      tasks: pedidos.tasks.exchange          # DIRECT
      dead-letter: pedidos.dlx               # DIRECT - DLX común
    queues:
      tickets:
        name: tickets.queue

    dead-letter:                             # retención de las DLQ

      initial-interval-ms: 1000

"Todos los nombres de colas, exchanges y bindings viven en el application.yml de cada servicio y se leen con @ConfigurationProperties. Ninguna clase escribe un nombre a mano."

3. Beans por caso de uso · 25 s

Muestra: config/TicketsTopologyConfig.java (hay una igual para notificaciones y otra para documentos).

@Configuration
public class TicketsTopologyConfig {
    // cola principal, con x-dead-letter-exchange
    @Bean Queue ticketsQueue(MessagingProperties props) {
        return TopologySupport.mainQueue(props.queues().tickets(), props);
    }
    // DLQ, con TTL y max-length (retención)
    @Bean Queue ticketsDlq(MessagingProperties props) {
        return TopologySupport.deadLetterQueue(props.queues().tickets(), props);
    }
    @Bean Binding ticketsBinding(@Qualifier("ticketsQueue") Queue queue,
            TopicExchange eventsExchange, MessagingProperties props) {
        return BindingBuilder.bind(queue).to(eventsExchange)
                .with(props.queues().tickets().bindingKey());
    }
    @Bean Binding ticketsDlqBinding(@Qualifier("ticketsDlq") Queue dlq,
            @Qualifier("deadLetterExchange") DirectExchange dlx,
            MessagingProperties props) {
        return BindingBuilder.bind(dlq).to(dlx)
                .with(props.queues().tickets().deadLetterKey());
    }
}

"La configuración de mensajería está aislada en el paquete config: un archivo por caso de uso con su cola, su DLQ y sus bindings."

5. ACK y manejo de errores · 40 s · el bloque más importante de la pauta

Muestra: messaging/AckingMessageProcessor.java, con acknowledge-mode: manual y prefetch: 1.

while (true) {
    attempt++;
    try {
        handler.accept(payload);
        channel.basicAck(tag, false);              // éxito
        return;
    } catch (PermanentProcessingException ex) {
        channel.basicNack(tag, false, false);      // permanente -> DLQ
        return;
    } catch (RuntimeException ex) {                // recuperable
        if (attempt >= retry.maxAttempts()) {
            channel.basicNack(tag, false, false);  // agotado -> DLQ
            return;
        }
        sleeper.sleep(delay);                      // espera 1 s, 2 s
        delay = Math.min((long) (delay * retry.multiplier()),
                retry.maxIntervalMs());
    }
}

"Cada consumidor confirma de forma explícita. Si el procesamiento sale bien hace ACK. Si el error es permanente, como un JSON inválido, hace NACK sin reencolar y el mensaje va directo a la DLQ. Si es recuperable, reintenta con espera creciente y, al agotar los tres intentos, lo manda a la DLQ. Nunca reencolamos en bucle, y un mensaje duplicado se confirma sin reprocesarlo."

Endpoints: POST /api/queues, GET y DELETE /api/queues/{name}, POST y DELETE /api/exchanges, POST y DELETE /api/bindings, GET /api/monitoring/queues. Muestra: dto/QueueCreateRequest.java

public record QueueCreateRequest(
        @NotBlank(message = "name es obligatorio")

"Toda la lógica de administración está en RabbitAdminService; los controladores solo llaman a sus métodos. Las entradas se validan con DTO: no se puede crear una cola con nombre vacío, con caracteres inválidos ni con el prefijo reservado amq.. Los errores vuelven en JSON con 400, 404 o 409, y modificar RabbitMQ exige el rol Admin."

Preguntas probables del docente

La pauta pide que cada integrante pueda fundamentar el diseño: los tres deben leer esta tabla.

PreguntaRespuesta corta
¿Diferencia entre DLX y DLQ?El DLX es un exchange que enruta los mensajes rechazados; la DLQ es la cola donde quedan guardados para revisarlos.
¿Por qué ACK manual?Para que el consumidor decida el destino de cada mensaje: ACK si salió bien, reintento si es transitorio, NACK sin reencolar hacia la DLQ si no tiene arreglo.
¿Cómo evitan un bucle infinito de reintentos?Máximo 3 intentos con espera de 1 s y 2 s; después NACK con requeue=false y el mensaje sale de la cola principal.
¿Por qué un exchange topic y uno direct?Topic para eventos que varias colas escuchan por patrón (pedido.*); direct para comandos con un solo destinatario por coincidencia exacta (documento.generar).
¿Qué pasa si RabbitMQ se cae?El pedido se guarda igual en la base de datos; el publicador registra el error en el log y no afecta la respuesta al usuario.
¿Las colas están replicadas en los dos nodos?No: son colas clásicas y viven en un nodo. Para alta disponibilidad real usaríamos quorum queues con 3 nodos; con 2, perder uno detiene la cola.
¿Qué retención tienen las DLQ?24 horas (x-message-ttl) y máximo 10.000 mensajes (x-max-length).
¿Cómo saben por qué un mensaje llegó a la DLQ?Por el log del procesador (NACK -> DLQ ... motivo=) y por el header x-death del mensaje, que dice la cola de origen y la razón.
¿Y si un mensaje llega dos veces?El procesador recuerda el messageId de los ya procesados y confirma el duplicado sin repetir el trabajo.
¿Dónde se valida el JWT?Dos veces: en el autorizador JWT del API Gateway (emisor y audiencia) y en cada microservicio con Spring Security (firma, emisor, audiencia, vigencia y roles).
¿Para qué @ConfigurationProperties?Lee los nombres del application.yml en un objeto tipado, así ningún nombre queda escrito a mano en el código.
¿Cómo simulan los errores?Con marcadores en la descripción del pedido (#FAIL-TICKET, #INVALID-NOTIFICACION, #FLAKY-TICKET), activados solo por configuración para la demostración.
